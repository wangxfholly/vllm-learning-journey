# 如何给单卡 vLLM 做性能优化:一周从出厂基线到瓶颈归因的完整复盘

> 一句话结论:单卡 Qwen2.5-7B-AWQ 服务,通过 L1 配置调优 + L2 逻辑优化 + L3 profiling 驱动,
> 在真实业务负载下把低并发 TTFT 从 122ms 降到 29ms(-76%),48 并发吞吐稳定在 1022 tok/s
> 且无长尾。但这篇文章真正想讲的不是数字,是「怎么定位瓶颈、怎么如实归因」。

## 一、背景

- 卡:单张 24GB 显存 GPU
- 模型:Qwen2.5-7B-Instruct-AWQ(INT4 量化)
- 引擎:vLLM 0.7.3
- 目标:支撑高并发企业级推理服务,为后续 Golang 网关多实例负载均衡打底

## 二、方法论:别上来就调参,先建立「定位-优化-验证」闭环

新手优化的通病是「凭感觉调参」——把 max_num_seqs 调大一点、显存利用率拉高一点,
跑一下感觉快了就收工。这是赌博,不是工程。

我用的是一套可复制的闭环:

1. **建立基线**(没有基线,所有「优化」都是错觉)
2. **定位瓶颈**(用 profiler 看 GPU 时间花在哪个算子,不靠猜)
3. **针对性优化**(瓶颈在哪打哪,别做无用功)
4. **A/B 验证**(每个改动都要有对照,证明收益真实存在)
5. **内部可观测**(用 /metrics 印证外部压测,形成闭环证据)

## 三、四个关键发现

### 发现 1:瓶颈是矩阵乘法(GEMM),不是 attention

用 PyTorch profiler 抓 trace 后,GPU 时间排行榜第一名是 Marlin kernel —— 
AWQ INT4 量化权重专用的 GEMM 算子,它占了 prefill 89.7% / decode 72.4% 的 GPU 时间。
而大家以为的瓶颈 flash attention,只占 1.1% / 0.7%。

认知升级:**优化前先 profile,否则你会花一周优化一个占 1% 时间的环节。**

注:profiling 必须在独占 GPU 上做。在线服务占着显存时根本加载不进离线模型,
这不是妥协,是方法论硬要求——带噪声的测量等于没测量。

### 发现 2:max_num_seqs 是「上限阀门」,不是「调节旋钮」

直觉以为 max_num_seqs 越大吞吐越高。A/B 实测打脸:
当实际并发没超过这个上限时,调它毫无影响;只有并发撞上上限,它才生效。
B 组(调到 32)在高并发下吞吐崩塌、P99 爆炸,完全如预测。

认知升级:**参数的语义比数值重要。搞清楚一个参数是「阀门」还是「旋钮」,再决定怎么动它。**

### 发现 3:prefix caching 是这一周最大的收益来源

企业服务普遍有很长的固定系统提示词(角色设定、工作规范)。
这段前缀每次请求都走一遍 Marlin 全量重算,是纯粹的浪费。
开启 prefix caching 后,字节完全相同的前缀,KV 直接命中缓存、整段跳过重算。
真实负载下低并发 TTFT 从 122ms 降到 29ms(-76%)。

认知升级:**最大的优化往往来自「消除重复计算」,而不是「让单次计算更快」。**

### 发现 4:缓存优化延迟,不优化吞吐天花板

冷启动 vs 热稳态,低并发 TTFT 差距巨大,但 48 并发吞吐完全重合(1022 tok/s)。
原因:并发拉高后瓶颈从「单请求 prefill 延迟」转移到「GPU 算力被 continuous batching 榨干」,
吞吐由物理算力天花板决定,缓存救不了算力。/metrics 还显示此时显存利用率仅 0.35%——
这张卡对短请求是「算力先到顶、显存大把富余」。

认知升级:**别指望一个优化解决所有问题。先分清你的瓶颈是延迟还是吞吐、是算力还是显存。**

## 四、最终生产配置与收益

python -m vllm.entrypoints.openai.api_server \
  --model <模型路径> \
  --quantization awq_marlin --gpu-memory-utilization 0.90 \
  --max-model-len 2048 --served-model-name qwen7b \
  --max-num-seqs 256 --enable-prefix-caching --port 8000

收益:
- 真实负载低并发 TTFT -76%(122ms → 29ms)
- 48 并发吞吐 1022 tok/s,P99 ≈ P50(128 vs 127),无长尾、无 preemption

## 五、最重要的认知升级

L1+L2+L3 这一周,最值钱的不是 1022 这个数字,是三件事:
1. 一切优化从「建立基线」开始,没有基线就没有优化;
2. 一切结论用 profiler 和 /metrics 证明,不靠感觉、不靠猜;
3. 收益如实归因——不为了好看的数字硬调,知道收益从哪来、边界在哪。
